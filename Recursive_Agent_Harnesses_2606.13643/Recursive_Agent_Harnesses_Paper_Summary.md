## 1. 개요 및 연구 동기 (Introduction & Motivation)

### 1.1 배경
현대 코딩 에이전트는 파일시스템 도구, 코드 실행 환경, 플래닝(기획) 역량 등을 결합한 **'에이전트 하네스(Agent Harness)'** 환경에서 동작하며 단일 컨텍스트 윈도우를 훨씬 넘어서는 방대한 문서를 탐색합니다. 그러나 수천 개의 독립적인 항목(entry)에 대해 개별적인 LLM 추론이 필요한 긴 컨텍스트 작업에서는 기존 접근 방식들이 명확한 한계를 드러냅니다.

### 1.2 기존 접근 방식의 맹점
| 접근 방식 | 대표 연구/사례 | 작동 방식 | 한계 및 맹점 |
| :--- | :--- | :--- | :--- |
| **코딩 에이전트 (Coding Agents)** | SWE-agent, Codex 등 | 파일시스템 도구를 통해 전체 문서를 탐색하고 스크립트를 작성하여 정규식(Regex) 등으로 일괄 처리 | 수천 개 항목을 단일 컨텍스트에 담을 수 없어, **항목별 LLM 추론을 생략하고 단순 정규식 휴리스틱에 의존** |
| **재귀적 언어 모델 (RLMs)** | Zhang et al. (2024) | 긴 입력을 재귀적으로 쪼개어(partition) **도구가 없는 순수 LLM 호출(model call)**을 재귀적으로 합성 | **파일시스템 접근, 셸 실행, 외부 도구 사용이 불가능**하여 검색 및 구조적 데이터 탐색 불가 |

### 1.3 핵심 질문 및 RAH의 착안점
> *"긴 컨텍스트 작업에서 에이전트가 재귀할 때, 재귀의 단위(recursive unit)는 도구가 없는 단순 모델 호출이어야 하는가, 아니면 도구와 실행 환경을 갖춘 '완전한 하네스'여야 하는가?"*

본 논문은 RLM의 '모델 재귀(Model Recursion)'와 프로덕션 코딩 에이전트(예: Anthropic의 Dynamic Workflows)의 서브에이전트 생성 패턴을 연결하여, **재귀의 단위를 도구·파일시스템·플래닝을 갖춘 완전한 에이전트 하네스로 격상한 '하네스 재귀(Harness Recursion)'**를 제안하고 이를 체계적으로 평가합니다.

## 2. RAH (Recursive Agent Harness) 핵심 구조 및 동작 원리

RAH는 부모 에이전트가 작업 부하(workload)의 크기에 따라 두 가지 경로를 통해 서브에이전트를 동적으로 생성(spawn)합니다.

```
                  ┌───────────────────────────────┐
                  │    Parent Agent (Harness)     │
                  │ - Context, Shell, File Tools  │
                  └───────────────┬───────────────┘
                                  │
          ┌───────────────────────┴───────────────────────┐
          │ (항목 수 1~5개)                               │ (항목 수 다수/대규모)
          ▼                                               ▼
┌───────────────────────────────┐               ┌───────────────────────────────┐
│   JSON Tool-Call Spawning     │               │    Code-Execution Spawning    │
│  - 직접 함수 호출(Task tool)  │               │  - 파이썬 실행 스크립트 생성  │
│  - API 호출 턴당 제한 존재    │               │  - asyncio.gather 병렬 실행   │
└───────────────┬───────────────┘               └───────────────┬───────────────┘
                │                                               │
                └───────────────────────┬───────────────────────┘
                                        ▼
                        ┌───────────────────────────────┐
                        │   Subagent Harnesses (1..N)   │
                        │ - 독립된 컨텍스트 및 워크스페이스 │
                        │ - 자체 도구(fs, shell, search)│
                        │ - 부모와 동일한 스폰 역량 보유│
                        │   (필요시 손자 에이전트 생성) │
                        └───────────────┬───────────────┘
                                        │ (결과 기록)
                                        ▼
                        ┌───────────────────────────────┐
                        │    Shared Output Aggregation  │
                        │ - 공유 JSON 파일에 결과 저장  │
                        │ - IPC 오버헤드 없는 집계      │
                        └───────────────────────────────┘
```

### 2.1 스폰(Spawning) 경로
1. **코드 실행 기반 스폰 (Code-Execution Spawning - 핵심 기여)**:
   - **원리**: 부모 에이전트가 `Task()` 객체를 인스턴스화하고 `asyncio.gather`를 통해 비동기 병렬 실행하는 독립 스크립트를 직접 작성한 뒤 셸 도구로 실행합니다.
   - **이점**: LLM API의 '턴당 병렬 툴 호출(parallel tool-call) 제한'을 완전히 우회하여, 수백~수천 개의 서브에이전트를 제한 없이 병렬로 구동할 수 있습니다.
   - **추상화**: 부모 에이전트는 서브에이전트의 중간 추론이나 파일 쓰기 과정을 보지 않고, 최종 집계된 표준 출력/공유 파일 결과만을 수신하여 컨텍스트 오염을 방지합니다.
2. **JSON 도구 호출 기반 스폰 (JSON Tool-Call Spawning)**:
   - 1~5개 수준의 소규모 항목인 경우, 스크립트 작성 오버헤드 없이 직접 구조화된 함수 호출로 서브에이전트를 생성합니다.

### 2.2 서브에이전트 아키텍처 및 진정한 재귀성 (Recursiveness)
- **독립 격리 환경**: 각 서브에이전트는 자신에게 할당된 엔트리, 문서 발췌본, 출력 형식 지침만을 포함하는 경계된 컨텍스트(bounded context)를 받으며, 형제 에이전트 간의 메모리 공유는 차단됩니다.
- **동일한 도구 및 하네스 기능**: `read_file`, `write_file`, `ls`, `glob`, `grep`, `execute`, 웹 검색 등 부모와 완벽히 동일한 도구 세트를 갖추고 추론 전 플래닝 단계를 수행합니다.
- **다단계 재귀 (Multi-level Recursion)**: 서브에이전트 또한 자체적인 스폰 역량을 지니므로, 복잡한 엔트리를 만나면 스스로 스크립트를 작성하여 손자 에이전트(grandchild harnesses)를 생성할 수 있습니다. (무한 확장을 막기 위해 기본 깊이 3으로 제한)
- **결과 수합**: 모든 서브에이전트는 지정된 경로의 공유 JSON 파일에 결과를 기록하며, 부모 스크립트가 이를 결정론적으로 집계합니다.

## 3. 실험 설계 (Experimental Setup)

### 3.1 벤치마크: Oolong-Synthetic
- **특징**: 수백만 토큰에 분산된 정보를 종합(aggregate)해야 하는 롱 컨텍스트 추론 벤치마크 (단순 검색 바늘 찾기형 태스크가 아님).
- **데이터셋 구성**: Oolong-Synthetic validation split에서 무작위 추출한 **199개 샘플**.
  - **컨텍스트 길이**: 1K부터 4M 토큰까지 총 **13개 버킷**으로 계층화(stratified) (인스턴스당 평균 629K 토큰).
- **평가 지표 (Oolong Score)**:
  - `LABEL`, `COMPARISON`, `USER`, `DATE`: 완전 일치(Exact Match).
  - `NUMERIC`: $0.75^{|y - \hat{y}|}$ (연속 수량에 대해 근사치에 점수를 부여하는 감쇠 공식).
  - 전체 199개 인스턴스에 대한 마이크로 평균 산출 (10,000회 리샘플링 95% 부트스트랩 신뢰구간 병기).

### 3.2 통제 조건 (Controlled Evaluation)
- 기존 최고 기준선(Codex)과의 공정한 비교를 위해 백본 모델을 **GPT-5 (`gpt-5-2025-08-07`)**로 동일하게 고정.
- 모델 성능 향상이 아닌 **하네스 아키텍처(Harness Architecture) 자체의 기여도**를 엄밀하게 분리 검증.
- 추가로 최신 고성능 모델인 **Claude Sonnet 4.5 (`claude-sonnet-4-5-20250929`)**를 백본으로 적용한 확장 실험 진행. (온도 0 고정)

## 5. 재귀 전략 비교 (Comparison of Recursion Strategies)

본 논문은 다양한 에이전트 및 재귀 패러다임을 **'재귀 단위(Recursive Unit)'** 관점에서 다음과 같이 명쾌하게 정리합니다:

| 전략 (Strategy) | 재귀 단위 (Recursive Unit) | 주요 장점 및 최적 사용처 |
| :--- | :--- | :--- |
| **코딩 에이전트 (Coding Agent)** | 없음 (단일 하네스 환경) | 파일 탐색 및 소수 항목 처리 |
| **모델 재귀 (Model Recursion, RLM)** | 단순 모델 호출 (도구 없음) | 외부 도구 접근이 필요 없는 순수 텍스트 분해 |
| **동적 워크플로우 (Dynamic Workflows)** | 스크립트로 생성된 서브에이전트 | 대규모 환경에서의 반복 가능한 오케스트레이션 |
| **하네스 재귀 (Harness Recursion, RAH)** | **완전한 에이전트 하네스 (Full Harness)** | **각 항목별 도구 사용 및 정밀 추론이 요구되는 대규모 태스크** |

## 6. 비용, 레이턴시 및 주요 실패 모드

### 6.1 비용(Cost) 및 레이턴시(Latency)
- **비용 요인**: 서브에이전트들이 공통 문서를 반복해서 읽는 비용이 주를 이룸.
  - 해결책: **프롬프트 캐싱(Prompt Caching)**을 적용하여 공통 컨텍스트 접두사를 재사용함으로써 토큰 비용을 **최대 80%까지 절감** 가능.
- **지연 시간**: `asyncio.gather`를 통해 모든 서브에이전트를 동시 병렬 실행하므로, 전체 소요 시간은 서브에이전트 수에 비례하는 것이 아니라 **가장 느린 단일 서브에이전트의 실행 시간**에 의해 결정됨.

### 6.2 실패 모드 (Failure Modes)
1. **스폰 생략 (Skipping Spawning)**: 매우 긴 컨텍스트에서 부모 에이전트가 스폰 스크립트를 작성하지 않고 문제를 단순 검색(retrieval)으로 오판하여 직접 답하려다 오답을 내는 현상 발생.
2. **NUMERIC 채점 지표 민감도**: 정량적 계산 추론이 거의 맞았음에도 $0.75^{|y-\hat{y}|}$ 지수 감쇠로 인해 1~2 차이로 점수가 크게 깎임.
3. **소표본 카테고리 분산**: DATE의 경우 표본 수가 5개에 불과하여 단 한 번의 실패로도 카테고리 점수가 크게 하락.

## 7. 한계점 및 향후 연구 과제 (Limitations)

1. **벤치마크 범위**: Oolong-Synthetic에 한정되어 있어, 증거가 모호하거나 비구조화된 실제 도메인(Oolong-Real 등)에 대한 일반화 평가는 추가 연구 필요.
2. **스크립트 생성 신뢰성**: 부모 에이전트가 구문 오류(syntax error) 없는 병렬 실행 코드를 안정적으로 생성해야 한다는 전제 조건이 따름.
3. **Ablation Study 부재**: 재귀 깊이 제한, 에이전트당 처리 항목 수, JSON vs 코드 실행 경로 간의 정밀한 절제 연구(ablation)는 향후 과제로 남김.

---

## 8. 총평 및 시사점 (Conclusion)

- **핵심 의의**: RAH는 초장문 컨텍스트(최대 4M 토큰)에 흩어진 수천 개의 항목을 처리할 때, 기존 코딩 에이전트의 '정규식 단축'과 RLM의 '도구 결여' 사이의 간극을 완벽하게 메웠습니다.
- **패러다임 전환**: LLM의 턴당 Tool-calling API에 얽매이지 않고, **'에이전트가 코드를 작성해 서브에이전트 하네스를 비동기 병렬로 직접 스폰'**하는 하네스 재귀(Harness Recursion) 방식이 향후 대규모 엔터프라이즈 문서 분석, 다중 문서 질의응답(Multi-document QA), 대규모 코드베이스 리팩토링의 표준 설계 패턴이 될 것임을 시사합니다.
